上一章讲的是函数调用在内存里怎么排列，每调用一次就压上一层栈帧，一层叠着一层。这一章讨论的是数据在内存里怎么排列，而数组是所有排列方式里最简单的一种，它的元素一个挨着一个存放，而且每个元素占的空间都一样大。

数组的性质只有这两条。后面提到的所有特点，比如查找为什么快、插入为什么慢、下标为什么从 0 开始、越界为什么没有人阻止，都可以从这两条推出来，不需要额外记忆。

这一篇不讲数组上的算法，插入、删除、查找、合并这些操作留到下一篇再讲。这一篇只讲数组本身，包括它怎么声明、存放在哪里、怎么扩容，以及编译器为什么一步就能找到 `A[i]`。最后一节是这一章的重点，也是唯一需要动笔计算的地方。

## 一、数组只有两条性质

第一条性质是，**元素在地址上是连续的**。比如 `int A[5]`，它的五个元素在内存里紧挨着存放，中间没有空出任何一个字节。

第二条性质是，**每个元素占的空间一样大**。这五个元素都是 `int`，每个都占 4 个字节。

有了这两条性质，只要知道首地址和下标，就能直接算出任何一个元素的位置，不需要从头开始一个一个地往后找。第一章说「数组的随机访问是 O(1)」，指的就是这件事。这并不是数组天生的优点，而是这两条性质带来的直接结果。

### 1.1 五种声明写法

![五种声明写法在内存里分别是什么样子](/img/posts/dsa-arrays/declare-five.svg)

*图 1：容量和初始值是两件不同的事情。*

```c
int A[5];                       // ① 容量 5，值是什么不知道
int B[5] = {2, 4, 6, 8, 10};    // ② 容量 5，五个值都给了
int C[5] = {2, 4};              // ③ 容量 5，给了两个，后三个是 0
int D[5] = {0};                 // ④ 容量 5，整块清零
int E[]  = {2, 4, 6, 8, 10};    // ⑤ 不写容量，由初始化列表定 —— 这里是 5
```

*代码 1：五种写法。*

运行结果如下：

```
A (未初始化): 0 0 0 0 0
B = {2,4,6,8,10}: 2 4 6 8 10
C = {2,4}: 2 4 0 0 0
D = {0}: 0 0 0 0 0
E = {2,4,6,8,10} 无长度: 2 4 6 8 10
sizeof(E) = 20, 元素个数 = 5
```

第 ③ 种和第 ④ 种写法值得单独说明一下。只要写了初始化列表，列表没有覆盖到的位置一律补 0，这是 C 标准规定的行为，并不是碰巧。所以 `= {0}` 才成了把整个数组清零的惯用写法，它依靠的并不是写在列表里的那个 0，而是这条补零规则。

第 ⑤ 种写法的容量是在编译期根据初始化列表数出来的。用 `sizeof(E) / sizeof(E[0])` 可以得到 5，这也是 C 语言里唯一能从数组本身得到长度的办法。不过这个办法只在能看到数组声明的地方有效，1.4 节会说明它在什么时候失效。

### 1.2 「垃圾值」是谁留下的

上面那次运行中，`A` 打印出来全是 0，这很容易让人以为不初始化也没有关系。但这只是碰巧。`main` 函数使用的是一块刚分配、已经被内核清零的栈页，所以读出来的值是 0。

只要换一个位置，问题就暴露出来了。先让一个函数在某块栈空间上写入一些数据，再让另一个调用深度相同的函数在同一块空间上声明一个未初始化的数组：

```c
void dirty(void) {              /* 先在这块栈空间上留下点东西 */
    int tmp[5] = {111, 222, 333, 444, 555};
    printf("dirty() 写入: ");
    for (int i = 0; i < 5; i++) printf("%d ", tmp[i]);
    puts("");
}

void fresh(void) {              /* 同样深度的另一个函数，用的是同一块栈空间 */
    int A[5];                   /* 没有初始化 */
    printf("fresh() 读到: ");
    for (int i = 0; i < 5; i++) printf("%d ", A[i]);
    puts("");
}

int main(void) {
    int A[5];                   /* main 自己那块，还没人动过 */
    printf("main 里直接读未初始化数组: ");
    for (int i = 0; i < 5; i++) printf("%d ", A[i]);
    puts("");
    dirty();
    fresh();
}
```

*代码 2：让「垃圾值」现原形。*

```
main 里直接读未初始化数组: 0 0 0 0 0
dirty() 写入: 111 222 333 444 555
fresh() 读到: 111 222 333 444 555
```

由此可见，所谓「垃圾值」并不是随机数，而是上一次使用这块内存的代码留下来的数据。声明一个数组只是划出一段地址，并没有任何人负责把它清理干净。清理是需要时间的，而 C 语言不会替程序员承担这笔开销。

这件事的实际后果是，读取未初始化的数组时，测试中的结果可能一直是正确的。如果那块内存碰巧是 0，程序就碰巧运行正常；等到某一天调用路径改变了，栈上换了别的数据，程序才开始出错。

### 1.3 下标就是地址算术

课上介绍了两种访问元素的写法，这里再多试了一种：

```c
int A[5] = {2, 4, 6, 8, 10};
printf("%d\n", A[2]);       // 6
printf("%d\n", *(A + 2));   // 6
printf("%d\n", 2[A]);       // 6 —— 也是合法的
```

*代码 3：三种写法，同一个元素。*

`2[A]` 居然也能通过编译，而且结果完全一样。

原因在于，C 标准对 `a[b]` 的定义本来就是 `*(a + b)`。加法满足交换律，所以 `A[2]` 和 `2[A]` 是同一个表达式。这种写法在实际中没有任何用处，但是它说明了一件事，那就是下标并不是专门用来访问数组的语法，它只是地址算术的简写。

地址也可以直接验证：

```
A         = 0x7ffc68a05a40
&A[0]     = 0x7ffc68a05a40      ← 数组名就是首地址
&A[2]     = 0x7ffc68a05a48
A+2       = 0x7ffc68a05a48      ← 和 &A[2] 完全相同
&A[2]-&A[0] 字节差 = 8, sizeof(int) = 4
```

两个地址相差 8 个字节，正好是 2 × 4。这说明指针加法是按元素计算的，而不是按字节计算的，`A + 2` 在地址上跳过的距离是 `2 × sizeof(int)`。到了第四节，这一点会写成一条正式的公式。

### 1.4 传进函数就不是数组了

```c
void f(int A[5]) { printf("函数里 sizeof(A) = %zu\n", sizeof(A)); }

int main(void) {
    int A[5];
    printf("main 里 sizeof(A) = %zu\n", sizeof(A));
    f(A);
}
```

*代码 4：同一个 `A`，两个 `sizeof`。*

```
main 里 sizeof(A) = 20
函数里 sizeof(A) = 8        ← 这是 sizeof(int*)
```

参数列表里的那个 `[5]` 只是写给人看的，编译器并不会使用它。数组作为参数传递时会退化成指向首元素的指针，长度信息在传参的那一刻就丢失了。gcc 甚至会直接给出提醒：

```
warning: ‘sizeof’ on array function parameter ‘A’
         will return size of ‘int *’
```

所以在 C 语言里，数组作为参数时总要额外传入一个长度。这并不是编程习惯的问题，而是因为这门语言没有别的办法。

## 二、静态数组与动态数组

### 2.1 差的是「容量还能不能换」

「静态」和「动态」这两个词很容易被理解成「值能不能修改」，但实际上两种数组的值都可以修改。它们真正的区别在于，容量确定之后还能不能换成一块更大的内存。

![数组住在哪，谁负责收尸](/img/posts/dsa-arrays/stack-vs-heap.svg)

*图 2：左边这块内存离开作用域后会自动释放，右边这块必须由程序自己归还。*

- **栈上的数组**（`int A[5]`）在进入作用域时整块分配，离开作用域时整块回收，不需要写 `free`。代价是它在运行过程中无法换成一块更大的内存，因为它的长度是类型的一部分。
- **堆上的数组**（`int *p = new int[5]`）在栈上只保存一个指针，数据本身放在堆里。它的长度可以是运行时才知道的值，也可以换成更大的一块，代价是程序必须自己调用 `delete[]` 释放它。

`sizeof` 能直接体现出这个区别。`sizeof(A)` 是 20，也就是整个数组的大小；`sizeof(p)` 是 8，也就是一个指针的大小。由于指针本身并不携带长度信息，堆上的数组同样需要程序自己记住长度。

### 2.2 长度能不能写成变量

`int n; cin >> n; int A[n];` 这种写法到底合不合法？常见的说法是「C 语言里数组长度必须是常量，C++ 里可以用变量」。下面直接让编译器来回答：

| 编译方式 | 结果 |
| --- | --- |
| `gcc -std=c99 -pedantic-errors` | 通过 |
| `gcc -std=c89 -pedantic-errors` | `error: ISO C90 forbids variable length array ‘A’` |
| `g++ -std=c++17 -pedantic-errors` | `error: ISO C++ forbids variable length array ‘A’` |
| `g++ -std=c++17`（不加 `-pedantic`） | 通过 |

结果和常见的说法正好相反。变长数组（VLA）是 C99 加入 C 标准的特性，C++ 标准里从来没有过；`g++` 之所以能够接受，只是因为它默认开启了 GNU 扩展，一旦加上 `-pedantic-errors` 就会报错。

和这件事相关的还有两点：

- C11 把 VLA 改成了可选特性。编译器可以通过定义 `__STDC_NO_VLA__` 表示自己不支持 VLA。这台机器上的 gcc 没有定义它，所以可以使用 VLA。
- VLA 分配在栈上。如果长度来自运行时的输入，那么长度就有可能由用户决定，`int A[n]` 中的 n 一旦很大，就会导致栈溢出。所以真正需要在运行时决定长度时，应该使用堆，而不是 VLA。

### 2.3 堆上的数组：申请与归还

```cpp
int *p = new int[5];            // C++
delete[] p;                     // 必须带 []，否则只析构第一个元素

int *q = (int*)malloc(5 * sizeof(int));     // C
free(q);
```

*代码 5：两套写法，各自配对，不能混用。*

这里有两件事不能出错。第一，`new[]` 要和 `delete[]` 配对，`malloc` 要和 `free` 配对，交叉使用属于未定义行为。第二，`delete[]` 的方括号不能省略。

### 2.4 扩容：三步，一步都不能少

栈上的数组无法更换，而堆上的数组也不能在原地直接变长，因为堆里紧跟在这块内存后面的位置，很可能已经分配给了别的数据。所以所谓扩容，实际上是另外找一块更大的内存，再把原来的数据搬过去。

![扩容：容量换不了，就换一块新的](/img/posts/dsa-arrays/grow-array.svg)

*图 3：这三步是一个整体，缺少任何一步都会产生一个 bug。*

```cpp
int *p = new int[5];
for (int i = 0; i < 5; i++) p[i] = (i + 1) * 2;     // 2 4 6 8 10

int *q = new int[10];                   // ① 另开一块大的
for (int i = 0; i < 5; i++) q[i] = p[i];//    把旧值搬过去
delete[] p;                             // ② 老的那块还给堆
p = q;                                  // ③ 名字接过来
q = nullptr;                            //    再把 q 清掉
```

*代码 6：扩容的三步。*

```
p (cap 5)  = 0x5872081f9ee0, 内容: 2 4 6 8 10
p (cap 10) = 0x5872081f9f30, 内容: 2 4 6 8 10 0 0 0 0 0
```

可以看到，扩容之后数组的地址变了，这是整个过程中最需要注意的一点。扩容之后，所有指向旧内存的指针都会失效。`std::vector` 在 `push_back` 之后可能导致迭代器失效，根本原因就在这里。

这三步分别对应一种 bug：

| 少了哪一步 | 后果 |
| --- | --- |
| ① 不拷贝 | 新块里全是垃圾值 |
| ② 不 `delete[]` | 旧块再也没人能还了 —— 内存泄漏 |
| ③ 不让 `p = q` | 名字还指着已经还掉的那块 —— 野指针 |

第三步最后的 `q = nullptr` 并不是可有可无的。如果保留 `q`，堆上的同一块内存就有两个名字，以后任何一个名字都有可能再被 `delete` 一次。

### 2.5 一次该扩多少

每次搬运数据的开销是 O(n)，所以每次扩容扩多少，直接决定了总的开销。下面实测两种策略：

| 插入 n 个元素 | 每次 +1 的拷贝次数 | 每次翻倍的拷贝次数 |
| --- | --- | --- |
| 10 | 45 | 15 |
| 100 | 4 950 | 127 |
| 1 000 | 499 500 | 1 023 |
| 10 000 | 49 995 000 | 16 383 |
| 100 000 | **4 999 950 000** | **131 071** |

如果每次只多申请一格，那么每插入一个元素，都要把前面所有的元素搬一遍，总的拷贝次数是 $1 + 2 + \cdots + (n-1) = \frac{n(n-1)}{2}$，也就是 O(n²)。插入 10 万个元素时，一共要搬运 50 亿次。

如果每次容量翻倍，搬运的总量是

$$
1 + 2 + 4 + \cdots + \frac{n}{2} < n
$$

加起来不超过 2n，平摊到每次插入上就是 O(1)。`std::vector` 采用的就是这种做法，这也是「均摊复杂度」这个概念最典型的例子。单看某一次 `push_back`，它可能很慢，因为正好赶上了扩容；但是把这次开销平摊到前面那些不需要扩容的插入上，每次插入的开销仍然是常数。

## 三、二维数组的三种声明

### 3.1 二维是画法，不是排法

`int A[3][4]` 在纸上画出来是 3 行 4 列，但是内存里并没有「行」和「列」的概念。第一章说过，内存地址是一维的，这里再验证一次：

```
=== int A[3][4] 的地址（相对首地址的字节偏移）===
  行 0:    0   4   8  12
  行 1:   16  20  24  28
  行 2:   32  36  40  44
  sizeof(A) = 48 字节，等于 3*4*4 = 48
  当成一维扫: 0 1 2 3 10 11 12 13 20 21 22 23
```

12 个元素的偏移从 0 一直排到 44，中间没有空出任何一个字节。所以「二维」只存在于下标的写法里，在内存中它就是一段连续的 48 字节。

### 3.2 三种写法

```cpp
int A[3][4];                    // ① 真正的二维数组：一整块

int *B[3];                      // ② 指针数组：3 个指针，每个指向一段
for (int i = 0; i < 3; i++) B[i] = new int[4];

int **C = new int*[3];          // ③ 二级指针：连指针数组本身也在堆上
for (int i = 0; i < 3; i++) C[i] = new int[4];
```

*代码 7：三种写法，下标写起来都是 `X[i][j]`。*

这三种写法访问元素时的下标写法完全一样，这也正是它们容易被当成同一种东西的原因。

![三种「二维数组」，在内存里是三样东西](/img/posts/dsa-arrays/two-d-layouts.svg)

*图 4：只有第一种写法得到的是一整块连续的内存。*

### 3.3 它们不是一回事

首先，`sizeof` 的结果不一样：

```
sizeof(A) = 48     ← 真的一整块
sizeof(B) = 24     ← 三个指针
sizeof(C) = 8      ← 一个指针
```

其次，行与行之间并不连续：

```
B[0] -> 0x637242489ec0
B[1] -> 0x637242489ee0
B[2] -> 0x637242489f00
行 0 与行 1 的字节距离 = 32
```

一行有 4 个 `int`，占 16 字节，但是相邻两行的首地址相差 32 字节。多出来的 16 字节是堆分配本身的开销，因为每块内存的前面要放一个块头，末尾还要按要求对齐。所以后两种写法得到的数组不能当成一维数组来遍历：

```
把方法二当成一维扫: 0 1 2 3 0 0 33 0
```

前 4 个值属于第 0 行，这没有问题；但是后 4 个值已经不是第 1 行了，它们是块头、对齐用的空间，以及碰巧落在那里的数据。用同样的方式遍历第一种写法，得到的则是完整的 12 个值。

最后，读取一个元素的开销也不一样。第一种写法只需要做一次乘法和一次加法，就能定位到元素；后两种写法要先读出行指针，再用这个指针去读元素，一共需要两次内存访问，而且这两次访问的地址毫无关系，所以缓存基本帮不上忙。

既然如此，为什么还需要后两种写法呢？因为它们能做到第一种写法做不到的事情。比如每一行的长度可以不同（锯齿数组），行数可以在运行时才确定；另外，当整个数组很大时，堆上可能凑得出几段零散的内存，却凑不出一整块连续的大内存。所以这几种写法是在做取舍，并没有绝对的优劣之分。

### 3.4 传参时列数不能省

```c
void ok (int A[][4], int rows) { /* ... */ }    // 可以
void bad(int A[][],  int rows) { /* ... */ }    // 编不过
```

*代码 8：第二个维度是必须写的。*

gcc 给出的错误信息是：

```
error: array type has incomplete element type ‘int[]’
note: declaration of ‘A’ as multidimensional array must have bounds
      for all dimensions except the first
```

这条规则并不是语法上的挑剔，而是因为下一节的地址公式里就用到了列数。如果不知道一行有几个元素，编译器就算不出 `A[i][j]` 的位置。第一个维度之所以可以省略，是因为公式里根本没有用到行数。

## 四、（重点）编译器怎么找到元素的位置

前面三节讲的都是数组的样子，这一节讲的是编译器拿到 `A[i]` 之后做了什么。整个过程只有一次乘法和一次加法，但是从这里出发，可以一次解释四个问题，分别是数组的下标为什么从 0 开始、越界访问为什么没有人阻止、行主序和列主序哪个更好，以及 n 维数组的地址应该怎么计算。

### 4.1 一维：一次乘法，一次加法

![编译器怎么找到 A[i]](/img/posts/dsa-arrays/address-1d.svg)

*图 5：「随机访问是 O(1)」这句话，说的就是这一行公式。*

设 $L_0$ 是数组的首地址（base address），$w$ 是一个元素占的字节数，那么

$$
\mathrm{Addr}(A[i]) = L_0 + i \times w
$$

对于 `int A[5]`，$w = 4$，所以 `A[2]` 位于 $L_0 + 8$，这和 1.3 节实测的 8 字节是一致的。

这个式子里最重要的一点是没有 n。无论数组有 5 个元素还是 5 亿个元素，无论要访问的是第 2 个还是第 5 亿个，都只需要做一次乘法和一次加法。O(1) 说的就是这件事，而不是「数组本来就快」。

反过来，链表就没有这样的公式。链表的节点分散在内存的各个地方，下一个节点在哪里只有上一个节点知道，所以只能顺着指针一个一个地往后找。数组和链表这两种物理结构之间的差别，最终就体现在有没有这条公式上。

### 4.2 为什么下标从 0 开始

如果下标从 1 开始，公式就要改成：

$$
\mathrm{Addr}(A[i]) = L_0 + (i - 1) \times w
$$

常见的解释是「这样每次访问都要多算一次减法，所以从 0 开始更快」。这个方向是对的，但是需要把程度说准确：多出来的只是每次访问多一次减法，只有一次，而不是很多次。

而且在实际的编译结果里，这一次减法往往连一条指令都不会多。下面把两种写法分别编译出来：

```c
int zero_based(int *A, int i) { return A[i]; }        /* 下标从 0 开始 */
int one_based (int *A, int i) { return A[i - 1]; }    /* 下标从 1 开始 */
```

*代码 9：只差一个 `- 1`。*

`gcc -O2` 的编译结果是：

```asm
zero_based:
        movsx   rsi, esi
        mov     eax, DWORD PTR [rdi+rsi*4]

one_based:
        movsx   rsi, esi
        mov     eax, DWORD PTR -4[rdi+rsi*4]
```

两者是同一条指令，只是后者多了一个 `-4` 的位移。x86 的寻址方式本来就有一个位移字段，用不用它速度都一样。也就是说，当下界是编译期常数时，减去 1 并不需要额外的开销。

真正会多出开销的，是下界要到运行时才能知道的情况，比如 Pascal 的 `array[lo..hi]`：

```c
int var_based(int *A, int i, int lo) { return A[i - lo]; }
```

```asm
var_based:
        sub     esi, edx            ← 这一条是真多出来的
        movsx   rsi, esi
        mov     eax, DWORD PTR [rdi+rsi*4]
```

所以准确的说法是，下标从 0 开始，是为了让「下标」和「偏移量」成为同一个数。这样公式里就没有修正项，指针算术、数组名和 `*(A+i)` 这几套写法才能完全对应起来。至于省下的那一点指令，只是附带的好处，并不是主要原因。

### 4.3 公式只会算，不会拦

既然读取元素就是套用一遍公式，那么把 `i` 写成 5 会发生什么呢？公式仍然会照常计算，$L_0 + 5 \times 4$ 是一个合法的地址，程序就会直接去读它。

把两个数组紧挨着放在一起，可以看得最清楚：

```c
struct Pair { int A[5]; int B[5]; };     /* 结构体成员按声明顺序排，B 紧跟在 A 后面 */

struct Pair s;
for (int i = 0; i < 5; i++) { s.A[i] = (i + 1) * 2; s.B[i] = 100 + i; }
printf("B 的首地址比 A 的大 %ld 字节 = 5 * 4\n",
       (char*)&s.B[0] - (char*)&s.A[0]);

int i = 5;                           /* 用变量绕开编译期常量折叠 */
printf("A[5] 读出来 = %d\n", s.A[i]);         /* 越界读 */
printf("A[7] 读出来 = %d\n", s.A[7]);
s.A[i] = -1;                                  /* 越界写 */
printf("给 A[5] 写了 -1 之后，B[0] = %d\n", s.B[0]);
```

*代码 10：越界读写。*

```
A = 2 4 6 8 10
B = 100 101 102 103 104
B 的首地址比 A 的大 20 字节 = 5 * 4
A[5] 读出来 = 100
A[7] 读出来 = 102
给 A[5] 写了 -1 之后，B[0] = -1
```

`A[5]` 读到的正好是 `B[0]`，`A[7]` 读到的是 `B[2]`，而往 `A[5]` 里写入 `-1`，就直接把 `B[0]` 改掉了。整个过程中，即使 gcc 开启了 `-Wall -Wextra`，也没有给出任何警告，运行时同样没有任何提示。

原因还是那条公式，编译器只负责计算地址，不负责判断这个地址是否还属于这个数组。C 语言没有边界检查，因为加上边界检查就意味着每次访问都要多做一次比较，还要额外保存数组的长度，而这门语言不愿意承担这些开销。

这也是数组最危险的地方。越界访问不会让程序当场崩溃，它只是悄悄修改了旁边那个变量的值。等到发现 `B[0]` 的值不对时，出错的现场早就不在了。

### 4.4 二维：行主序与列主序

对于二维数组，需要把 `(i, j)` 这一对下标转换成一个偏移量，转换的方式有两种。

![同一张表，两种铺法](/img/posts/dsa-arrays/row-col-major.svg)

*图 6：每一行用一种颜色表示，可以看出这些颜色在直线上是怎么排列的。*

第一种是**行主序（row major）**，也就是排完一行再排下一行。第 i 行前面有 i 个完整的行，每行有 n 个元素，再加上本行内的 j 个元素，就得到：

$$
\mathrm{Addr}(A[i][j]) = L_0 + (i \times n + j) \times w \qquad (n = \text{列数})
$$

第二种是**列主序（column major）**，也就是排完一列再排下一列。同理可以得到：

$$
\mathrm{Addr}(A[i][j]) = L_0 + (j \times m + i) \times w \qquad (m = \text{行数})
$$

C 和 C++ 使用的是行主序，Fortran 和 MATLAB 使用的是列主序。下面用 `int A[3][4]` 验证一下行主序：`A[2][1]` 的偏移应该是 $(2 \times 4 + 1) \times 4 = 36$，实测的偏移量也正好是 36。

这两种映射方式的速度是一样的，而且是真的一样，并不只是差不多。把两条公式分别编译出来，结果如下：

```asm
row_major:  imul esi, ecx        col_major:  imul edx, ecx
            add  esi, edx                    add  edx, esi
            mov  eax, [rdi+rsi*4]            mov  eax, [rdi+rdx*4]
```

两边都是一次乘法、一次加法和一次取数，指令的形式完全相同。所以选择哪一种完全取决于语言设计者，哪一种都不吃亏。

### 4.5 算得一样快，走得不一样快

上一小节说的是计算一个元素的地址时，两种方式一样快。但是如果要把整个数组遍历一遍，情况就完全不同了。

![算地址一样快，走的顺序不一样快](/img/posts/dsa-arrays/cache-line.svg)

*图 7：每次访问内存都会搬回一整条缓存行，搬回来的数据能不能用上，取决于遍历的顺序。*

下面对同一个数组求和，只是把两层循环的顺序对调：

```cpp
for (int i = 0; i < N; i++)                     // 按行走
    for (int j = 0; j < N; j++) a += M[i][j];

for (int j = 0; j < N; j++)                     // 按列走
    for (int i = 0; i < N; i++) b += M[i][j];
```

*代码 11：两段代码的区别只在于 `i` 和 `j` 谁在外层。*

| 矩阵 | 占用 | 按行走 | 按列走 | 慢几倍 |
| --- | --- | --- | --- | --- |
| 512×512 | 1 MB | 0.05 ms | 0.22 ms | 4.1 × |
| 1024×1024 | 4 MB | 0.21 ms | 2.40 ms | 11.3 × |
| 2048×2048 | 16 MB | 0.83 ms | 17.77 ms | **21.5 ×** |
| 4096×4096 | 64 MB | 3.38 ms | 64.80 ms | 19.2 × |
| 8192×8192 | 256 MB | 14.18 ms | 300.68 ms | 21.2 × |

（每一档都重复运行多次，取最快的一轮，整组实验跑了三遍。规模较大的那几档稳定在 20 倍左右。）

两种写法求出的和完全相等，访问次数也完全相同，计算地址的公式同样便宜，所以慢二十倍的原因并不在公式里。

原因在于 CPU 每次从内存搬运的数据不只 4 个字节，而是一整条**缓存行**，在这台机器上是 64 字节，也就是 16 个 `int`。按行遍历时，搬回来的 16 个数接下来都会用到，平均访问 16 次才真正需要等待一次内存；按列遍历时，每走一步都会跳过一整行，搬回来的 16 个数只用到 1 个，剩下的 15 个还没来得及使用，就已经被挤出了缓存。

表格里最小的那一档只差 4 倍，这是因为 1 MB 的矩阵可以完整地放进这个核心自己的 L2 缓存（每个核心 1 MB），即使跳着访问也不会超出缓存范围。从下一档开始，差距就稳定在二十倍左右了。

所以在行主序和列主序之间做选择，真正的影响并不在于计算地址，而在于它决定了哪一种遍历顺序是顺着内存地址进行的。C 语言采用行主序，所以在 C 语言的双重循环里，应该把 `j` 放在内层。这种写法本身没有任何额外成本，却能带来二十倍的性能差距。

### 4.6 推广到 n 维：把公式提一提

三维数组 `int A[2][3][4]` 可以看成「2 个 3×4 的表」，它们仍然连续地排在一条直线上。一层一层地往里推，可以得到：

$$
\mathrm{Addr}(A[i][j][k]) = L_0 + \bigl((i \times 3 + j) \times 4 + k\bigr) \times w
$$

代入 `A[1][2][3]`，算出的偏移是 $((1 \times 3 + 2) \times 4 + 3) \times 4 = 92$，实测的偏移也正好是 92（24 个元素都逐个核对过，全部一致）。

推广到 n 维，设各维的大小是 $d_1 \times d_2 \times \cdots \times d_n$，下标是 $i_1, i_2, \ldots, i_n$。如果把每一项都直接展开，公式是这样的：

$$
\mathrm{Addr} = L_0 + \bigl(i_1 d_2 d_3 \cdots d_n + i_2 d_3 \cdots d_n + \cdots + i_{n-1} d_n + i_n\bigr) \times w
$$

数一下其中的乘法次数，第一项要乘 $n-1$ 次，第二项要乘 $n-2$ 次，以此类推，最后还要再乘一个 $w$，一共是

$$
\frac{n(n-1)}{2} + 1 \;=\; O(n^2)
$$

![推广到 n 维：把公式提一提](/img/posts/dsa-arrays/ndim-horner.svg)

*图 8：这和上一章泰勒展开那道题用的是同一种方法。*

不过这些项里有大量重复的公因子。如果从里往外逐层提取公因子，公式就变成了：

$$
\mathrm{Addr} = L_0 + \Bigl( \bigl( \cdots ((i_1 d_2 + i_2) d_3 + i_3) d_4 \cdots \bigr) d_n + i_n \Bigr) \times w
$$

这样一来，每多一维只多一次乘法，一共是 n 次，也就是 O(n)。实测两种写法算出的地址完全一致，乘法次数则如下表所示：

| 维数 n | 朴素展开 | 提取公因式后 |
| --- | --- | --- |
| 3 | 4 | 3 |
| 5 | 11 | 5 |
| 10 | 46 | 10 |

这就是上一章 6.4 节泰勒展开的第二种写法，也就是秦九韶算法（Horner 法则）。同一种方法出现在两个毫不相干的地方，说明它并不是某一道题的特殊技巧，而是一种通用的思路。如果一串项里反复出现相同的公因子，就可以从里往外把它提出来，从而省掉重复的乘法。

当然，实际代码里很少会用到超过三维的数组，从 O(n²) 降到 O(n) 省下的只是常数级别的工作量。这个推导之所以值得记住，是因为它展示了地址公式能够推广到什么程度。从一维的 $L_0 + iw$ 一直推广到 n 维，中间没有用到任何新东西，始终都是同一条规则。

## 小结

| 要点 | 一句话 |
| --- | --- |
| 数组的全部性质 | 地址连续，每个元素等宽，其余性质都由这两条推出 |
| 初始化 | 只要写了初始化列表，没有覆盖到的位置一律补 0 |
| 垃圾值 | 不是随机数，而是上一次使用这块栈空间的代码留下的数据 |
| 下标 | `a[b]` 的定义就是 `*(a+b)`，所以 `2[A]` 也能通过编译 |
| 传参 | 数组传进函数后会退化成指针，长度必须另外传入 |
| 静态 / 动态 | 区别不在于值能否修改，而在于容量能否更换 |
| 变长数组 | 是 C99 的特性，C++ 标准里没有，g++ 能接受是因为编译器扩展 |
| 扩容 | 拷贝、`delete[]`、接管指针这三步缺一不可；扩容后旧指针全部失效 |
| 扩多少 | 每次加 1 是 O(n²)，每次翻倍是均摊 O(1) |
| 二维的三种写法 | 只有 `int A[3][4]` 是一整块连续内存，另外两种是指针数组加若干段内存 |
| 地址公式 | $L_0 + i \times w$，式子里没有 n，所以随机访问是 O(1) |
| 从 0 开始 | 为了让下标就是偏移量；当下界是常数时，省下的那次减法本来也不花时间 |
| 越界 | 公式只负责计算地址，不负责检查，结果会悄悄改掉相邻变量的值 |
| 行 / 列主序 | 计算地址一样快，但遍历顺序会造成二十倍的差距 |
| n 维 | 提取公因式后，乘法次数从 O(n²) 降到 O(n)，和泰勒展开那道题是同一种方法 |

总结起来，数组的所有特点，都可以从「地址连续」和「每个元素等宽」这两条性质推出来。查找快，是因为能直接计算地址；越界不报错，是因为算出地址后就直接使用；按列遍历慢，是因为算出来的地址是跳跃的。

下一章会在这块连续的内存上实现各种操作，包括插入、删除、查找和合并。这一章靠地址公式得到的随机访问能力，在下一章会继续用到；而连续存放带来的代价，也会在下一章体现出来，因为在中间插入一个元素时，后面的元素都必须让出一格。
