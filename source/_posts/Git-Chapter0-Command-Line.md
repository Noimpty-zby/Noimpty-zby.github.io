Git 课的第一节不讲 Git，讲命令行。一开始觉得这是凑时长，学完才明白为什么必须放在前面：**Git 的每一条命令都不接收「你要操作哪个项目」这个参数。** 它靠的是你敲命令时人在哪个文件夹里。所以在敲出第一个 `git init` 之前，得先能随时回答「我现在在哪儿」。

这一篇记的就是那段速成里的十来条命令。它们看起来是十来个互不相干的小知识点，但按课程顺序抄一遍表格意义不大——真正值得写下来的是：**这些命令几乎全都在围着同一个东西转，就是 Shell 的「当前工作目录」。** 想通这一点之后，`.` 是什么、`..` 是什么、为什么文件建到了别的地方去、`rm -rf` 到底危险在哪，就不再是四个问题，而是一个。

<!-- more -->

> 这些命令在「Linux 入门」那条线里也会讲，而且讲得更细。重合的部分这里不重复写——比如「为什么 `clear` 清不掉历史记录」这种「这件事归谁管」的问题，[Linux 命令行第一章](/2026/08/25/Linux-Command-Line-Chapter1/) 里已经整理过了。这一篇只按 Git 课的取舍来记，落点是「进 Git 之前必须有的那点手感」。

## 一、当前工作目录：命令行里唯一的「我在哪」

图形界面里，「我在哪个文件夹」这件事是**看得见**的：窗口标题写着，地址栏也写着，换一个窗口就换一个位置。命令行里没有窗口这个概念，取而代之的是一个藏起来的状态——**当前工作目录（current working directory）**。Shell 一直记着它，但默认不告诉你。

把它打印出来的命令是 `pwd`：

```bash
pwd
# /home/zby/projects/git-study
```

*代码 1：`pwd` 是 print working directory 的缩写。*

它输出的是一条**绝对路径**——从根目录 `/` 一路写到当前位置，不依赖任何上下文。这个东西之所以重要，是因为后面几乎每条命令都会拿它当默认参数：

- `ls` 不带参数时，列的是**它**里面的东西
- `touch a.txt` 建出来的文件，落在**它**里面
- `git init` 初始化的仓库，就是**它**

换句话说，你敲的每条命令后面其实都跟着一个看不见的「在这里」。**命令出乎意料的时候，第一个该敲的往往是 `pwd`。**

## 二、ls：看这个位置里有什么

`ls` 是 list 的缩写，把当前工作目录里的内容列出来：

```bash
ls              # 列当前位置
ls projects     # 列 projects 这个子目录里的东西，人不动
ls projects/git-study   # 往下钻两层，中间用 / 分隔
```

*代码 2：`ls` 的三种常见用法。*

第二、三行值得单独说一句：**`ls 某个目录` 只是「看一眼那边」，并不会把你带过去。** 看完之后 `pwd` 的输出一个字都没变。「看」和「走」在命令行里是两条不同的命令，这跟图形界面里双击一下就既看了又进去了不一样，刚上手时很容易混。

### `-a`：隐藏文件不是一种属性

```bash
ls -a
# .  ..  .git  .gitignore  README.md  src
```

*代码 3：`-a` 是 all，把隐藏的一并列出来。*

这里有个当时以为是「系统给文件加了个隐藏标记」、其实完全不是的事：**Unix 里所谓的「隐藏文件」，只是名字以 `.` 开头的文件而已。** 文件系统没有「隐藏」这个属性，是 `ls` 自己默认跳过这类名字，Shell 的通配符展开也默认不匹配它们。所以「隐藏」纯粹是一个**命名约定**，谁都能隐藏一个文件——改个名字加个点就行。

这条对 Git 特别关键，因为接下来要打交道的两个东西都以点开头：`.git`（整个仓库的家底）和 `.gitignore`（忽略清单）。**不加 `-a` 的 `ls` 永远看不见它们**，于是很容易产生「我这个文件夹里什么都没有」的错觉。

顺带记住输出开头那两个东西：`.` 和 `..`。它们不是 `ls` 印出来凑数的符号，而是**每个目录里真实存在的两个条目**——`.` 指向这个目录自己，`..` 指向它的上一层。下一节的 `cd ..` 就是直接用的它。

### `-l` 与选项合并

`-l`（long）把每一项摊开成一行，显示权限、属主、大小和修改时间。短选项可以拼在一起写：

```bash
ls -la          # 等价于 ls -l -a
```

*代码 4：短选项合并。*

`ls -la` 大概是这门课里出现频率最高的一条命令，因为它同时解决了「有什么」和「里面有没有 `.git`」两个问题。

## 三、cd：换一个位置

`cd` 是 change directory 的缩写，作用是**真的把当前工作目录换掉**——`pwd` 的输出会跟着变。

```bash
cd projects        # 进入子目录（相对路径）
cd ..              # 回退一层
cd /home/zby       # 直接跳到某个绝对位置
cd                 # 不带参数：回到家目录
cd -               # 回到上一次待的地方
```

*代码 5：`cd` 的五种写法。*

前两行是**相对路径**：它们的含义取决于你现在在哪儿，同一条 `cd ..` 在不同位置执行会到达不同的地方。第三行是**绝对路径**，以 `/` 开头，走到哪儿敲都是同一个结果。这个区别在 Git 里会反复出现——比如 `git add .` 里的那个点，就是一条相对路径。

`cd ..` 之所以能回退，不是因为 `cd` 认识 `..` 这个咒语，而是因为**上一节说的那个 `..` 条目是真实存在的**，`cd` 只是老老实实地走了进去。同理，`cd .` 是合法的，只是等于原地不动；`../..` 就是往上退两层。

两个实用的小东西：**Tab 键会补全路径**，敲前几个字母按一下就行，既省事又能顺手验证「这个目录名我没打错」；**路径里有空格必须加引号或转义**，否则 Shell 会按空格把它切成两个参数，命令根本不知道你说的是同一个文件夹。

## 四、touch 与 mkdir：在这个位置上造东西

```bash
touch notes.md          # 创建一个空文件
mkdir git-study         # 创建一个目录
mkdir -p a/b/c          # 一次把缺的层级全建出来
```

*代码 6：创建文件与目录。*

`mkdir` 是 make directory 的缩写，没什么歧义。`-p`（parents）值得记一下：默认的 `mkdir a/b/c` 在 `a` 不存在时会直接报错，加上 `-p` 就会把中间缺的目录一并建出来，而且目标已经存在时也不报错。

`touch` 则有一个当时被顺口带过、其实名不副实的地方：**它的本职工作根本不是建文件，而是更新文件的时间戳**（touch 就是「碰一下」的意思）。只有当目标文件不存在时，它才顺手建一个空的出来——这是副作用，不是主业。

这带来一个好消息和一个坏消息。好消息是：**对已存在的文件执行 `touch`，不会清空它**，只是把修改时间刷成现在，所以不用担心手滑 `touch` 一下把写好的东西弄没了。坏消息是：正因为它「存在就不动」，你没法靠它的成功与否判断文件是不是新建的——两种情况都是静默成功。

还有一个从 Windows 带过来的习惯要改：**`.md`、`.txt` 这些扩展名对 Unix 系统本身没有任何意义**，它只是文件名的一部分，系统不会因为你写了 `.md` 就把它当 Markdown 处理。真正在乎扩展名的是编辑器、Git 的某些配置和你自己。所以 `touch notes` 和 `touch notes.md` 造出来的是同样合法的两个文件，只不过后者更能让工具（和三个月后的你）看懂。

## 五、rm：删，而且没有回收站

```bash
rm notes.md             # 删一个文件
rm -r old-project       # 递归删一个目录（连同里面所有东西）
rm -rf old-project      # 递归 + 强制，不问任何问题
rmdir empty-dir         # 只能删空目录，非空就报错
```

*代码 7：删除。⚠️ 这几条都没有确认步骤。*

第一件必须先记住的事：**`rm` 不是「移到回收站」，是直接把目录项摘掉，默认既不确认也不可撤销。** 图形界面里删错了还能从回收站捞回来，这里没有那一层。

把 `-rf` 拆开看，它其实是两个独立的选项，各自解决一个「拦路」的问题：

| 选项 | 全称 | 它关掉了什么 |
| --- | --- | --- |
| `-r` | recursive | 默认 `rm` 拒绝删目录，`-r` 让它递归进去，把子目录和文件一并删掉 |
| `-f` | force | 不提示、不报错，目标不存在也当成功 |

所以 `-r` 是「让它能删目录」，`-f` 是「让它闭嘴」。**危险的是这两个凑在一起**：`-r` 扩大了打击面，`-f` 又把所有本来能拦你一下的提示全关了。

真正会出事的场景，恰好又落回第一节那个「当前位置」上。`rm -rf *` 这条命令本身没有指定任何具体路径，它删的是**「我现在这个位置下的所有东西」**——所以它的破坏范围完全取决于你敲下回车那一刻 `pwd` 的值。在项目子目录里执行是清理，在家目录里执行就是灾难，而这两次敲的字符一模一样。

而且通配符不是 `rm` 展开的，是 **Shell 在启动 `rm` 之前就替换好**的：你写 `*`，`rm` 收到的是一串已经列好的具体文件名。等到 `rm` 开始跑的时候，「要删哪些」这件事早就定死了，没有任何反悔的余地。

所以从这门课开始养成两个习惯：**删之前先 `pwd`**，确认自己站对了地方；**危险的删除先用 `ls` 把同样的参数跑一遍**，看清楚会命中哪些文件再动手：

```bash
ls *.log        # 先看会命中哪些
rm *.log        # 确认无误再删
```

*代码 8：把 `ls` 当成 `rm` 的预演。*

对 Git 来说还有一条额外的红线：**`rm -rf .git` 会把整个版本历史一次删光。** 工作区里的文件看起来一个没少，但所有提交记录、所有分支、所有还能回滚的版本全没了——而且这恰恰是 `rm -rf` 唯一救不回来的东西，因为 Git 的后悔药本身就存在 `.git` 里面。

## 六、两条不改变位置的辅助命令

`clear` 清空当前终端窗口的显示。它只是让终端重画一遍屏幕，**命令历史一条没少**，按 ↑ 照样能翻出来（原因在 [Linux 命令行第一章](/2026/08/25/Linux-Command-Line-Chapter1/) 里写过：显示归终端管，历史归 Shell 管）。快捷键是 `Ctrl + L`，比敲命令快。

`open .` 则是在图形界面里打开当前工作目录，等于给命令行和文件管理器搭了座桥。这条命令**各个平台不一样**：

| 环境 | 命令 |
| --- | --- |
| macOS | `open .` |
| Windows（CMD / PowerShell） | `start .` |
| Linux 桌面 | `xdg-open .` |
| WSL | `explorer.exe .` |

注意末尾那个 `.`——它就是第二节里说的「当前目录」那个条目。这条命令没有任何魔法，它只是**把「这里」交给了图形界面去打开**，所以它打开哪个窗口，同样由 `pwd` 决定。刚上手时它其实是个不错的验证手段：命令行里造完文件，`open .` 一下用眼睛确认一遍，比反复 `ls` 更踏实。

## 小结

这一章的十来条命令，按「它和当前工作目录是什么关系」重新排一遍，就只剩三类：

| 命令 | 和「当前位置」的关系 |
| --- | --- |
| `pwd` | **问**它是什么 |
| `ls` / `ls -a` / `ls -l` | **看**它里面有什么 |
| `open .` / `start .` | 把它交给图形界面打开 |
| `cd` / `cd ..` / `cd -` | **改**它 |
| `touch` / `mkdir` | 在它里面**造**东西 |
| `rm` / `rm -rf` | 在它里面**删**东西 |
| `clear` | 唯一一条和它无关的（只管屏幕） |

一整列都指向同一个隐含参数。所以命令行里「明明敲对了却出了怪事」，十有八九不是命令写错了，而是**人站错了地方**——文件建到了上一层、`ls` 看不到刚下载的东西、删掉了不该删的目录，全是同一个原因。

这也正是这段速成必须放在 Git 前面的理由。Git 的命令同样不接收「操作哪个项目」这个参数：`git init` 把**当前目录**变成仓库，`git status` 报告**当前仓库**的情况，`git add .` 里的那个点就是**当前目录**。整套 Git 都建立在这个隐含参数上，只不过它比 `rm` 客气一些——站错地方的时候，它一般只是告诉你 `not a git repository`。
