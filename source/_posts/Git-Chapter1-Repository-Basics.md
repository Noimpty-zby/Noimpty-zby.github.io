正式开始 Git 了。这一章的命令不多，`init` / `status` / `add` / `commit` / `log` 加一个 `.gitignore` 文件，照着敲全都能跑通。但跑通和搞懂是两回事——**真正卡人的不是命令本身，而是 `git status` 的输出为什么长那样。**

`Changes to be committed`、`Changes not staged for commit`、`Untracked files`，同一个文件甚至能同时出现在两栏里。这些话只有在知道「Git 把东西分成了三个地方存」之后才读得懂。所以这一篇不按命令排，按**地方**排：先讲清有哪三个区，再看每条命令负责哪一段搬运。搞清楚这个之后，上面那几行英文就不用查了，它是在念一张地图。

## 一、仓库到底是什么

课程里说 repository（仓库）是「Git 真正工作的地方」。这句话对，但抽象。落到地上，仓库就是一个具体的、能用 [上一章](/2026/09/05/Git-Chapter0-Command-Line/) 的命令看见的东西：

```bash
git init
ls -a
# .  ..  .git
```

*代码 1：`git init` 之后多出来的那个目录。*

`git init` 干的事情就是**在当前目录里建了一个 `.git` 文件夹**，仅此而已。你的项目文件一个字节都没动，只是旁边多了个以点开头、默认看不见的目录。所谓「这个文件夹被 Git 管起来了」，物理上就是「它里面有个 `.git`」——所有的提交记录、分支、配置全都存在这里面，删掉它，这个文件夹立刻变回一个普通文件夹。

这里有两件事值得先钉住：

**第一，`git init` 作用在当前工作目录上。** 它不接收「初始化哪个项目」这个参数，跟上一章那十来条命令是同一个套路。所以**敲 `git init` 之前先 `pwd`**——在家目录里手滑初始化一次，Git 会开始盯着你整个用户目录，然后每次 `git status` 都吐出成千上万个未跟踪文件。这也是仓库不该嵌套的原因：在一个已经是仓库的目录里再 `init` 一个，两层 Git 会互相看不见对方的文件。

**第二，第一次用之前得先自报家门。** 每一次提交都要记下作者是谁，没配的话 `git commit` 会直接失败，而不是用个默认值糊弄过去：

```bash
git config --global user.name "Noimpty"
git config --global user.email "you@example.com"
```

*代码 2：`--global` 表示对这台机器上所有仓库生效，配一次就够。*

## 二、三个地方，不是两个

这是整章的骨架。一次改动从「你敲下的字」到「进了历史」，中间要过两道门、经过三个地方：

```
工作区(Working Directory)  --git add-->  暂存区(Staging Area)  --git commit-->  仓库(Repository)
   你正在编辑的文件                      挑好的、准备提交的内容              .git 里的永久记录
```

工作区就是你能用编辑器打开的那些文件；仓库是 `.git` 里那份不可变的历史；夹在中间的**暂存区**是唯一一个新概念，也是唯一一个「明明可以没有、但 Git 偏要有」的设计。

它存在的理由是：**一次改动和一次提交，不该被强行绑定。** 写代码的时候你很可能同时改了三个文件——两个是真正在做的功能，第三个只是顺手调了个配置。如果只有「改了就提交」两个状态，这三个文件必须一起进历史，提交记录就会变成一锅粥。有了暂存区，你可以先把那两个挑进去提交成一条干净的记录，第三个留在工作区里下次再说。

**暂存区是「挑」的地方，不是「存」的地方。** 这句话是后面所有命令的解释来源。

## 三、git status：读那张地图

`git status` 是唯一一条能告诉你「此刻每个文件在哪一区」的命令，而且它的输出就是按上面那三个地方分栏的：

| 输出里的栏目 | 含义 | 这些文件在哪 |
| --- | --- | --- |
| `Untracked files` | Git 从没见过的新文件 | 工作区，且完全没被追踪 |
| `Changes not staged for commit` | 追踪过、改了、但没 `add` | 工作区 |
| `Changes to be committed` | 已经 `add` 过，等着提交 | 暂存区 |
| `nothing to commit, working tree clean` | 三个地方内容一致 | —— |

Git 还很贴心地在每一栏下面直接印出了「你现在可能想敲哪条命令」。**刚上手的阶段，每敲一条命令之后都跑一遍 `git status`**，比背命令有用得多——它会把每条命令实际搬动了什么直接摆给你看。

顺带解释一个词：**未跟踪（untracked）不等于被忽略。** 它只是说「这个文件 Git 还没管过」，一旦 `add` 过一次，它就变成被追踪的了，此后每一次改动 Git 都会盯着。这个区别在第八节讲 `.gitignore` 时会变成一个大坑。

## 四、git add：工作区 → 暂存区

```bash
git add notes.md            # 暂存单个文件
git add notes.md src/a.go   # 一次暂存多个
git add .                   # 暂存当前目录下的所有改动
```

*代码 3：`add` 的三种写法。*

第三行那个 `.` 就是上一章说的「当前目录」，不是什么特殊语法。这意味着两件事：一是它**会递归包括子目录**；二是**它只从你现在站的地方往下看**——如果你人在 `src/` 里面，`git add .` 抓不到仓库根目录下别处的改动。想不管站在哪都全抓，用 `git add -A`。

然后是这一节真正的重点，也是当时理解错、后来被 `git status` 教育了才改过来的一点：

> **`git add` 暂存的是「文件此刻的内容」，不是「这个文件」。**

它拍的是一张快照。所以下面这个流程的结果会很反直觉：

```bash
git add notes.md      # 暂存 A 版本
# ……接着又改了 notes.md，变成 B 版本
git status            # notes.md 同时出现在两栏里
git commit -m "..."   # 提交的是 A，不是 B
```

*代码 4：`add` 之后再改，改动不会自动跟进。*

同一个文件同时出现在 `Changes to be committed`（A 版本）和 `Changes not staged for commit`（B 版本）两栏里，一开始看着像 Git 出了 bug，其实它说的完全准确：**暂存区里躺着 A，工作区里放着 B，这就是两份不同的内容。** 提交只认暂存区，所以出来的是 A。

想提交 B，只要再 `git add` 一次——把新快照覆盖上去就行。这个坑的实际杀伤力在于它**不报错**：提交成功、命令全绿，只是提交进去的不是你以为的那一版。所以那句「每敲一条命令跑一遍 `git status`」在这里是真能救命的。

## 五、git commit：暂存区 → 仓库

```bash
git commit -m "写清楚这次改了什么"
```

*代码 5：`-m` 是 message，不写它 Git 会打开编辑器让你输入。*

要记住的就一条：**`commit` 打包的是暂存区的内容，工作区里没 `add` 的改动一律不进这次提交。** 上一节那个坑的另一半就在这儿。

关于 message，课程里提到的写法在协作里确实是通行惯例：**用现在时的祈使句描述这次提交「做了什么」**，比如 `add gitignore for build output`，而不是 `added...` 或者 `我加了 gitignore`。理由挺实际的——Git 自己生成的提交（比如合并）用的就是这个语气，保持一致读起来才顺。至于内容，写「为什么这么改」的价值远高于「改了哪些行」，因为后者 `git diff` 随时能看，前者只有你此刻知道。

提交完成后，这次改动就有了一个**永久的、以 SHA 哈希为名字的身份**，从此可以被随时找回来。这也是整套 Git 敢让人放手乱改的底气：只要提交过，就丢不了。

## 六、git log：读仓库里的历史

```bash
git log
git log --oneline
```

*代码 6：完整历史与精简历史。*

`git log` 按时间倒序列出提交，每条带上完整的 SHA、作者、日期和 message。`--oneline` 把每条压成一行——**缩写的 SHA 加一句 message**，屏幕上一次能看十几条，看「最近都干了什么」用它。

这里第一次见到的那串十六进制就是提交的 SHA。缩写版通常是前七位，日常引用够用了；后面撤销、比较、变基那些命令，参数往往就是从这里复制出去的。所以 `--oneline` 不只是排版好看，它是**后面所有「回到某个版本」操作的入口**。

## 七、git commit --amend：不是修改，是替换

场景很常见：刚提交完就发现漏了一个文件，或者 message 打错了字。为这点事再来一条提交会让历史变脏，`--amend` 就是干这个的：

```bash
git add forgotten.md          # 先把漏掉的补进暂存区
git commit --amend            # 连同上一次提交一起重新打包
git commit --amend --no-edit  # 只补文件，message 保持原样
```

*代码 7：`--amend` 会把暂存区的内容并入上一次提交。*

但「修改上一次提交」这个说法其实是个善意的谎言。Git 的提交对象是不可变的，**`--amend` 做的是造一个新提交，然后让分支指过去**——原来那条并没有被改写，只是没人再指向它了。最直接的证据是 SHA 变了：amend 之后再 `git log --oneline`，最上面那条的哈希和刚才不是同一个。

这直接推出一条硬规矩：**已经推送到远程的提交不要 amend。** 因为对别人来说，那条旧提交还在他们的历史里；你这边换了个新 SHA，两边的历史就从那一点开始分叉了，再推上去 Git 会直接拒绝，硬推则会把别人的记录冲掉。**只对还没推出去的最后一次提交用它**，这是安全的边界。

这条规矩对这个博客尤其现实——仓库里挂着几个定时任务会自动往 main 上提交，「远程已经变了」不是假想的教学例子，是每天都在发生的事。所以 amend 之前先确认一句：这条提交只在我本地待过吗？

## 八、.gitignore：把文件拦在第一道门外

有些文件根本不该进版本历史：编译产物、依赖目录、日志、系统自动生成的垃圾，还有密钥。办法是在仓库根目录建一个名为 `.gitignore` 的文件（又是一个以点开头的隐藏文件，`ls -a` 才看得见），每行写一条规则：

```gitignore
.DS_Store        # 按文件名忽略：macOS 访达在每个文件夹里生成的那个
secrets.env      # 忽略指定的某个文件
node_modules/    # 末尾的斜杠表示只匹配目录，整个文件夹连同内容一起忽略
*.log            # 通配符：所有以 .log 结尾的文件
!important.log   # 感叹号是反向规则：把上一条排除掉的这个再捞回来
```

*代码 8：几种常见写法。*

有两个细节课程里没展开，但踩过一次印象很深：

**第一，不带斜杠的规则会匹配任意层级。** 写 `.DS_Store` 会忽略仓库里所有目录下的同名文件，不只是根目录那个。反过来，如果规则中间带了 `/`（比如 `build/output`），它就变成从 `.gitignore` 所在目录算起的路径，只匹配那一处。

**第二，也是那个真正的坑——`.gitignore` 只对「还没被追踪」的文件有效。**

一个文件只要 `add` 或 `commit` 过一次，它就成了被追踪的文件，此后无论 `.gitignore` 里怎么写，Git 都照样盯着它的改动。这个行为很反直觉，但它是对的：忽略清单管的是「要不要把新东西纳进来」，而不是「要不要把已经在里面的东西踢出去」。

**表现出来就是：明明写进了 `.gitignore`，`git status` 里它还在。** 解决办法是先把它从追踪列表里摘掉：

```bash
git rm --cached secrets.env
```

*代码 9：`--cached` 表示只从 Git 的追踪里删，磁盘上的文件保留。*

那个 `--cached` 千万不能漏——不加的话 `git rm` 会连磁盘上的文件一起删掉，而它要是从来没提交过，就真的没了。摘掉之后再提交一次，`.gitignore` 才会开始对它生效。

最后一个容易忘的点：**`.gitignore` 本身是要提交进仓库的。** 它是项目配置的一部分，得让每个克隆这个仓库的人都拿到同一份忽略规则，否则各人的 `git status` 会看到不同的东西。

## 小结

把这一章的六条命令按「它在三个区之间搬了什么」重排一遍：

| 命令 | 它做的事 |
| --- | --- |
| `git init` | 在当前目录建 `.git`，仓库从这一刻开始存在 |
| `git status` | 报告每个文件现在处于哪一区（唯一的地图） |
| `git add` | 工作区 → 暂存区，搬的是**内容快照** |
| `git commit -m` | 暂存区 → 仓库，工作区里没 add 的一律不带 |
| `git log` / `--oneline` | 读仓库里的历史，顺便拿到 SHA |
| `git commit --amend` | 用新提交替换最后一次（SHA 会变，推过就别用） |
| `.gitignore` | 让文件根本不进第一道门（但拦不住已经进去的） |

两个当时以为是 Git 出错、其实是自己理解错的地方，值得单独记一笔：

- **`add` 之后再改，提交的还是 add 那一刻的版本**——因为暂存的是内容不是文件；
- **写进 `.gitignore` 的文件还在 `git status` 里**——因为忽略只管未追踪的文件。

这两个坑有一个共同点：**它们都不报错。** 命令成功、终端全绿、历史照样往前走，只是里面装的东西和你以为的不一样。这大概是 Git 最需要适应的一件事——它几乎从不阻止你，只是忠实地记录你实际做了什么。所以 `git status` 才该是敲得最频繁的那条命令：它是唯一会把「Git 眼里的现状」和「你以为的现状」摆在一起对照的地方。
