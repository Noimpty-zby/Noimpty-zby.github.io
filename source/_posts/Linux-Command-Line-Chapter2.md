第二章是「怎么自己查」。课程里讲了 `man`、`type`、`which`、`help` 四条命令，看起来是四个查文档的小工具，随便挑一个能用的用就行。

但试了几次之后发现它们并不能互相替代：`man cd` 查不到东西，`which cd` 也什么都不返回，`help ls` 同样报错。**四条命令各自有各自查得到和查不到的范围，而这个范围是由「你查的那个名字是什么东西」决定的。**

所以这一篇的顺序和课程反过来：先讲 `man` 怎么读，再讲当 `man` 失效时该怎么办——那部分正好接着 [第一章](/2026/08/25/Linux-Command-Line-Chapter1/) 的那张分工图往下走。

## 一、man：内容归 man 管，翻页归另一个程序管

`man` 是 manual pages（使用手册）的缩写，用法就是后面跟一个命令名：

```bash
man ls
```

*代码 1：打开 `ls` 的手册。*

回车之后整个终端会被手册占满，这时候键盘不再是在敲命令了，而是在操作一个**翻页器**。常用的几个键：

| 键 | 作用 |
| --- | --- |
| `q` | quit，退出手册回到命令行 |
| `f` / `空格` | forward，向后翻一屏 |
| `b` | back，向前翻一屏 |
| `↑` / `↓` | 一次滚一行 |
| `g` / `G` | 跳到手册开头 / 结尾 |
| `/内容` | 向后搜索，回车确认 |
| `n` / `N` | 跳到下一个 / 上一个搜索结果 |
| `h` | help，列出翻页器自己的按键说明 |

最后那个 `h` 当时理解错了：**它给的不是「这个命令有哪些选项」，而是「翻页器自己有哪些按键」。** 搜索、跳转、标记，全是翻页这件事的说明书，和 `ls` 一个字的关系都没有。

这个区别不是记混了那么简单，它是第一章那张分工图的又一个实例。`man` 本身只负责**找到并格式化**那份文档，把内容显示成一屏一屏、响应你的按键的，是另一个叫 **`less`** 的程序（这一点在 `man --help` 里能直接看到：它有一个 `-P, --pager=PAGER` 选项，而下一行的 `-r, --prompt` 说明里写着 the `less` pager——翻页器是可以被换掉的一个外部依赖）。两个程序串在一起，所以按键手册和内容手册是两份东西。

顺带一个连带的好处：**`less` 的这套键在别的地方也能用。** 后面遇到 `git log`、`less 大文件` 之类会占满屏幕的东西，翻页键完全一样，因为背后是同一个程序。

## 二、SYNOPSIS 那一串方括号怎么读

打开手册之后最先撞上的是 SYNOPSIS（概述），长这样：

```
NAME
       ls - list directory contents

SYNOPSIS
       ls [OPTION]... [FILE]...
```

*代码 2：`ls` 手册的开头两段。*

这一段是整份手册里信息密度最高的地方——它用一行写完了这条命令所有的合法写法。规则就几条：

| 写法 | 含义 |
| --- | --- |
| `[ ]` | 方括号里的东西**可省略** |
| `...` | 前面那个东西可以**重复出现多次** |
| `\|` | 竖线两边**二选一** |
| 加粗的字 | **原样照抄**，一个字符都不能改 |
| 斜体 / 下划线的字 | **占位符**，要换成你自己的东西 |

所以 `ls [OPTION]... [FILE]...` 翻译过来是：`ls` 这三个字母必须照写；后面可以跟任意多个选项，也可以一个都不跟；再后面可以跟任意多个文件名，也可以一个都不跟。这正好解释了为什么 `ls`、`ls -l`、`ls -l a.txt b.txt` 三种写法全都合法。

手册再往下的几段也值得知道各自装了什么，不然容易从头读到尾：

- **DESCRIPTION** —— 详细说明，通常也是选项清单的所在地
- **EXAMPLES** —— 例子，有的话优先看这里，比 DESCRIPTION 快得多
- **EXIT STATUS** —— 退出状态码的含义，写脚本判断成败时要查
- **SEE ALSO** —— 相关命令，顺藤摸瓜的入口

实际用起来最高效的路径其实是：打开手册，直接 `/-l` 搜到那个选项，看完就 `q`。**手册是拿来查的，不是拿来读的。**

## 三、8 个章节：同一个名字可能是好几样东西

手册被分成了 8 个部分（section），平时查命令用到的 user commands 只是第一部分：

| 章节 | 内容 |
| --- | --- |
| 1 | 用户命令（平时敲的那些） |
| 2 | 系统调用（内核提供的接口） |
| 3 | 库函数（C 标准库这类） |
| 4 | 特殊文件与设备（`/dev` 下面的东西） |
| 5 | 文件格式与约定（配置文件长什么样） |
| 6 | 游戏 |
| 7 | 杂项与综述 |
| 8 | 系统管理命令（一般要 root） |

分章节不是为了整理得好看，而是因为**同一个名字在不同层次上确实是不同的东西**。最典型的是 `passwd`：它既是一条改密码的命令（第 1 章），又是 `/etc/passwd` 这个文件的格式说明（第 5 章）。直接 `man passwd` 只会给你第一个找到的，也就是第 1 章那条命令。

指定章节的写法是把编号放在名字前面：

```bash
man 5 passwd      # 只看第 5 章：/etc/passwd 的文件格式
man -a passwd     # 所有章节挨个看，q 一次跳到下一个
man -k passwd     # 按关键词搜：所有简介里提到 passwd 的手册页
```

*代码 3：三条容易记混的写法。*

这三条我当时全串在一起了，实际上区别很清楚：

- **`man 5 名字`** —— 我知道要哪一章，直接去那一章。
- **`man -a 名字`** —— 我不知道有几章，全都过一遍。`-a` 是 all。
- **`man -k 关键词`** —— 我连命令叫什么都不知道，让它去搜。

第三条最值得单独说，因为它和前两条根本不是一回事。**`-k` 不是「看这个命令的全部信息」，而是拿关键词去搜所有手册页的名字和一句话简介**（它等价于另一条叫 `apropos` 的命令）。所以它的用途是反着来的——不是「我知道命令名，想看它怎么用」，而是**「我知道我想干什么，但不知道该用哪条命令」**：

```bash
man -k "list directory"
# ls (1)  - list directory contents
# dir (1) - list directory contents
```

*代码 4：`-k` 是从「想做的事」倒查「该用的命令」。*

这里有个坑：`man -k` 查的不是手册本身，而是一个预先建好的索引数据库。新装的系统或者刚装完某个软件时，可能会得到一句 `nothing appropriate`——不是真没有，是索引还没建。跑一次 `sudo mandb` 重建就好了。

## 四、man 查不到的时候：先搞清这个名字是什么

到这里为止都很顺，直到试了这一条：

```bash
man cd
# No manual entry for cd
```

*代码 5：查不到。*

第一反应是「文档没装全」。但真正的原因要有意思得多：**`cd` 根本不是一个程序，所以它没有自己的手册页。**

回到第一章那张图——命令分两种。一种是磁盘上真实存在的可执行文件（`ls` 就是 `/usr/bin/ls` 这个文件），Shell 找到它、启动一个新进程去跑；另一种叫 **Shell 内建命令（builtin）**，它是 Shell 这个程序自己身上带的功能，不需要启动任何新进程。

`cd` 必须是后者，而且**只能**是后者。理由是：`cd` 要改变的是「当前工作目录」，而这个状态存在 Shell 自己身上。假如 `cd` 是个独立程序，Shell 启动它、它改掉的只是它自己那个新进程的工作目录，然后它一退出，一切原样——你会得到一条敲了没有任何反应的命令。所以 `cd` 不可能被做成程序，它必须由 Shell 亲自执行。

这一节的三条命令，回答的就是「这个名字属于哪一种」。

### type：最该先敲的那条

`type` 直接告诉你这个名字会被当成什么来处理：

```bash
type cd
# cd is a shell builtin

type man
# man is /usr/bin/man

type ls
# ls is aliased to `ls --color=auto'
```

*代码 6：三种不同的答案。*

它能给出四类结果：**别名（alias）、Shell 内建（builtin）、函数（function）、外部程序（给出完整路径）**。这四类正好对应四种查文档的方式，下面小结那张表就是照着它排的。

第三行顺带解开了一个疑惑：为什么很多系统上 `ls` 的输出是彩色的，可手册里根本没说默认带颜色？因为你敲的 `ls` 早就被换成了 `ls --color=auto`——**别名是 Shell 在调用命令之前做的替换**，跟第一章里 `$HOME` 的展开是同一类事情。

还有一个 `-a` 选项，会把所有同名的东西全列出来：

```bash
type -a echo
# echo is a shell builtin
# echo is /usr/bin/echo
```

*代码 7：同一个名字，两个不同的东西。*

（有的系统上还会多出一行 `/bin/echo`——那不是第三个 echo，只是因为 `/bin` 本身就是指向 `/usr/bin` 的软链接，同一个文件被数了两遍。）

`echo` 同时以内建和外部程序两种形式存在，而**内建优先**。这意味着一件挺违反直觉的事：`man echo` 打开的是 `/usr/bin/echo` 那份手册，但你敲 `echo` 实际跑的是 Shell 内建的那个。两者绝大多数时候行为一致，但选项支持上确实有出入——所以当手册写的和实际跑出来的对不上时，先 `type -a` 看一眼是不是查错了对象。

### which：只认磁盘上的文件

`which` 的作用是**告诉你某个程序的可执行文件在哪**：

```bash
which man
# /usr/bin/man

which cd
#（什么都没有）
```

*代码 8：`which` 对内建命令无能为力。*

它查不到 `cd` 不是 bug。`which` 的做法是拿名字去 `PATH` 里列的那几个目录挨个找同名文件，而 `cd` 在磁盘上**根本没有对应的文件**，自然找不到。

更根本的原因是：**`which` 自己就是一个外部程序。** 它是被 Shell 启动的另一个进程，站在 Shell 外面，看不见 Shell 内部的别名、函数和内建。`type` 则是 Shell 内建的，它是从里面看的——所以 `type` 知道的永远比 `which` 多。**能用 `type` 的时候就别用 `which`。**

### help：内建命令的说明书

内建命令没有 man 手册，但不代表没有文档。查它们要用 Shell 自己提供的 `help`：

```bash
help cd
# cd: cd [-L|[-P [-e]] [-@]] [dir]
#     Change the shell working directory.
#     ...
```

*代码 9：内建命令的文档在 Shell 手里。*

注意 `help` 和 `--help` 是两个完全不同的东西，只是长得像：

- **`help 名字`** —— 一条独立的命令（本身也是内建的），只管 Shell 内建命令的文档。`help ls` 会报错，因为 `ls` 不是内建。
- **`命令 --help`** —— 传给那个程序的一个**选项**，由程序自己打印一段简介。能不能用取决于程序作者写没写。

所以查外部程序的简版文档用 `ls --help`，查内建命令用 `help cd`，两边不通用。

## 小结

这一章的四条命令，按「名字是什么东西」重排一遍，就变成了一张查询表：

| `type` 说它是 | 例子 | 该用什么查 |
| --- | --- | --- |
| 别名 alias | `ls` | `type` 就能看到它被换成了什么 |
| Shell 内建 builtin | `cd` / `echo` / `pwd` | `help 名字` |
| 函数 function | 自己或配置文件里定义的 | `type 名字` 会直接打出定义 |
| 外部程序（一个路径） | `man` / `sort` | `man 名字`，或者 `名字 --help` |

所以顺序应该是：**先 `type` 问清楚这是什么，再决定用哪种方式查文档。** 上来就 `man` 只是因为大部分命令恰好是外部程序，撞上内建的那几个就会莫名其妙地失败。

回头看，第一章的结论是「一件事归谁管」，这一章其实是同一句话换了个问法——**一个名字归谁管**。`cd` 归 Shell，`ls` 归磁盘上那个文件，而 `echo` 两边都有一份。搞不清归属就查不到文档，这跟文档写得全不全没关系。
