## 工程实践与踩坑

- **pprof 提案拟给 heap profile 补上 RSS 分层视图** —— Go 的 runtime/pprof 一直只展示存活堆，默认 GOGC=100 下这块通常不到进程 RSS 的一半，得手动拼 RSS、runtime/metrics、heap profile 三份数据才能看清内存全貌。Felix Geisendörfer 提的 proposal #79179 要在 heap/alloc profile 里加 memory_space 采样类型，并设成 pprof.Lookup("heap") 的默认输出，把「RSS → Go 内存/非 Go 内存 → 堆/栈/运行时」放进一份 profile，提案已标记 active 并获 Austin Clements 等核心成员原则性认可。对你意味着：以后查 Go 服务内存不用再自己拼三份数据，但这是提案不是已发布版本，现在线上还得照旧手动对齐 RSS 和 heap。我觉得这个提案戳的是真实痛点——只看 live heap 排查内存问题基本等于半瞎，值得盯它的落地进度。 [来源 · tonybai.com](https://tonybai.com/)

- **Go 写堡垒机的并发卖点：goroutine 扛上万路 SSH 会话** —— 素材讲的是用 Go 实现企业级堡垒机，4A 架构加 SSH 代理，核心论点是堡垒机最重的场景是大量 SSH 会话同时建立，Go 的 goroutine 能扛上万路并发连接，内存占用比 Java 线程模型低一个数量级，部署也简单。但素材只给了架构卖点，没给任何压测数字、版本号或可复现步骤。对你意味着：如果你在做后端或 AI Infra 里的连接密集服务，goroutine 模型确实是对的方向，但这条只能当选题参考，不能当性能结论用。我觉得它更像架构综述而非踩坑实录，真想验证得上自己的压测，光看「低一个数量级」这种话没有说服力。 [来源 · bbs.csdn.net](https://bbs.csdn.net/weixin_33491377/article/details/100396749)
