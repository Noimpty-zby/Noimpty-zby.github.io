## 面试与求职干货

- **快手测试开发岗校招面经流出 MySQL 到 Agent 权限题都有**。素材里是 2025 年 2 月 20 日和 3 月 5 日的两轮面经。一面考了 MySQL 事务隔离级别、MVCC、缓存穿透击穿雪崩的区别、HashMap 底层、线程池核心参数、线上慢 SQL 排查、索引失效场景，还有力扣 128 最长连续序列。二面开始往 Agent 方向走，问 Agent 知识库怎么防止恶意会话请求和绕过权限、稠密向量和稀疏向量区别，接着又回 Java 问了强软弱虚引用、ThreadLocal、索引下推、Lock 与 synchronized、公平锁非公平锁，手撕力扣 560。这套题对他的用处比较直接，MySQL、缓存、慢 SQL 和索引正好是他常备的方向，Agent 知识库权限和向量题也能拿来补 AI Infra 的面试短板。我觉得快手这套题说明测试开发岗已经在混考后端和 Agent 基础了，如果目标是快手，传统八股和 AI 应用安全都不能只准备一边。 [来源 · nowcoder.com](https://www.nowcoder.com/enterprise/898/interview)

- **MySQL LIKE 查询把 Buffer Pool 挤出 220ms 延迟的案例**。素材讲的是 InnoDB 的 Buffer Pool 本来用来缓存热数据页，但 LIKE 查询的访问模式是全量、随机、一次性，会把 text 字段所在的冷数据页强行装进来，挤掉原本缓存的高频主键索引页和热点商品详情页。有一场大促前压测里，一条 LIKE '%预售%' 的后台报表查询让后续 3 分钟内订单查询 P95 延迟上升 220ms。链路是 B+ 树不支持中间匹配导致全表扫描，CPU 被字符串比对吃满，Buffer Pool 被冷数据塞爆。文章还顺带讲了 ES text 和 keyword 类型区别，举了 brand 字段被 ik 分词器切成单字的例子。这对他很有用，答 MySQL 慢查询优化时不只是背「LIKE 不走索引」，还能把缓存污染这个层面讲出来，同时解释 ES 倒排索引为什么能替代这种搜索场景。我觉得这个案例比一般的 Like 索引失效有价值，因为真正的问题是冷数据页把整个实例的热点缓存打脏了，线上看到连接数突增和慢日志暴增的时候可以先往这个方向查。 [来源 · bbs.csdn.net](https://bbs.csdn.net/weixin_32430941/article/details/100714390)

- **一条 Agent Skill 设计高频题讲透了 Tool 和常驻提示词的边界**。素材是码良发的一条推文，讲 Agent 面试高频题里的 Skill 怎么设计。他的观点是 Skill 数量暴涨往往是因为把每个细碎动作都拆成了独立 Skill，原子操作应该收进 Tool 或同一个 Skill 的不同脚本参数里，Skill 对应的是完整业务场景 SOP。给相邻 Skill 写 description 时要标明互斥条件，比如离线数仓 Hive SQL 调优和在线事务 MySQL 慢查询分别走不同技能。他还算了常驻提示词的账，系统提示词和 CLAUDE.md、AGENTS.md 是会话级常驻开销，每一轮推理都要全量算注意力，所以代码评审规范、PR 模板、慢查询手册这类内容不该全塞进去。这条对他准备 AI Infra 或 Agent 后端面试有用，Skill 和 Tool 的划分、上下文预算控制都是可能会被追问的点。我觉得互斥条件直接写进 description 这个做法比笼统说「别建太多 Skill」更好落地，而且把常驻提示词当每轮固定成本来算，比单纯背「减少 token」更能解释清楚上下文优化的理由。 [来源 · x.com](https://x.com/cxjwin/status/2116171741504602363)

## 工程实践与踩坑

- **MQTT 从 500 台扩到 5 万台时踩的坑**。博客园这篇写了扩容后的几类故障：Broker 重启后上万设备同时重连形成重启风暴，靠客户端指数退避加随机抖动、Broker 侧限连接速率来压住；大量 CleanSession=false 导致会话爆炸，要设 session_expiry_interval；还有全链路 QoS2 四次握手把吞吐压低，遥测和告警改回 QoS1。另外提到遥测原始消息不能直接写 MySQL 主表，要按时序库规划，单实例不够就按设备 ID 哈希分库分表。我觉得这篇对做 IoT 后端的价值在它把每个坑和修法配了对，比如重启风暴那个抖动的思路，换成任何长连接服务都通用，可以直接抄去检查自己的重连逻辑。 [来源 · cnblogs.com](https://www.cnblogs.com/hugogoos/p/23446857)

- **Go SIMD 在 amd64 和 arm64 上的内存对齐差异**。这篇给了三个线上踩坑的最小复现 case 和修复方案，其中第一个是 amd64 对内存对齐比较宽容、arm64 严格，同一段向量化代码在 x86 上跑得好好的，换到 arm64 就可能出问题。素材没说具体版本和报错内容，只说这是最普遍也最容易被忽视的一类问题。我觉得这条对他有用的地方是提醒：现在不少服务跑在 arm64 云主机上，用 SIMD 或 unsafe 做优化的代码，本地 amd64 测过不代表线上 arm64 没问题，得在目标架构上跑一遍。 [来源 · bbs.csdn.net](https://bbs.csdn.net/weixin_30702441/article/details/100703764)
