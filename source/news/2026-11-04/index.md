## 面试与求职干货

- **Linux 内核 TCP 竞态漏洞被评为 Critical，但下游发行版评分明显更低**。CVE-2026-98432 是 Linux 内核 IPv4 TCP 握手路径上的竞态条件导致的 use-after-free，Linux kernel CVE team 在 10 月 15 日发布，10 月 24 日给出 CVSS 3.1 9.8 分，也就是网络可达、无需凭据和用户交互。Red Hat、Oracle、SUSE 给 8.1 分，Amazon 给 7.0，Red Hat 自身发布的数据则在 5.9 到 8.1 之间。素材标题称目前还没有 RHEL 或 Ubuntu 修复，同时没有厂商、CERT 或 kernel CVE team 报告在野利用。对他有用的是，后端同学如果负责线上 Linux 服务器，不能只看 CVE 编号的 Critical 就恐慌，也要跟发行版安全公告，特别留意补丁发布时间和缓解措施；面试聊到 Linux 内核安全时，能把 race condition 和 UAF 两类问题连起来讲，会比只报漏洞编号更有说服力。我觉得这条最有意思的是评分分歧本身，它说明同一条内核问题在不同发行版的暴露面差异很大，做后端该建立的判断是看自己实际暴露的服务和内核版本。 [来源 · rescana.com](https://www.rescana.com/post/linux-kernel-tcp-cve-2026-98432-use-after-free-prepare-now)

- **索引比数据还大，考查的是索引维护成本**。一条推文式面试题提到，面试官问「索引比数据还大了」时，回答要落到两点：insert、update、delete 都要同步维护所有相关索引，所以写入会变慢；二级索引单独存储，冗余索引还会白白占磁盘和 Buffer Pool。素材本身没有展开更多例子，只给了这两个方向。这题考查的是你能不能把索引当成有存储和写入代价的结构来看，难度对后端入门偏中低，但只背八股的人容易只答查询收益。我觉得这道题虽然短，但它把索引当成有维护成本的结构来问，适合在准备 MySQL 时用来检查自己是否只记了查询收益，没有考虑冗余索引怎么来的。 [来源 · x.com](https://x.com/cxjwin/status/2117800260730802347)

- **MySQL 升级到 8.0 后 P99 翻倍，问题可能不在 SQL 而在于统计信息**。11 月 1 日一篇排查案例提到，同样是没改过的 SQL，MySQL 升级到 8.0 后接口 P99 反而翻倍；里面强调不要拿索引名称代替执行成本，也不要看到 EXPLAIN 里命中了索引就认为性能正常。案例里举例千万行订单表按状态索引扫描时，为了返回 20 条记录可能要检查大量候选行，还可能回表或额外排序。MySQL 8.0 支持直方图，但升级后不会自动给字段创建。对他有用的是，后端面试或项目复盘时，如果碰到升级后慢查询，要知道去对比新旧环境的表规模、索引定义、估算行数和真实扫描行数，必要时更新统计信息再观察执行计划。我觉得这条比单纯背《高性能 MySQL》更贴近实际，它把「用索引名判断性能」这个常见误区点破了，准备面试时很适合拿来练如何解释 rows、filtered 和回表成本。 [来源 · tianqi.csdn.net](https://tianqi.csdn.net/6ae74ef1e5f4ca4eff8dbbc6.html)

## 工程实践与踩坑

- **Claude 挖出的内核漏洞牵连到默认开启 MPTCP 的 Go 服务**。Anthropic 用 Claude 发现了 Linux 内核高危漏洞 CVE-2026-98432，还构造了针对 MPTCP 监听服务的远程 root 利用链。Go 1.24 起默认启用 Linux MPTCP Listener，所以不少 Go 网络服务可能受影响。对你来说，如果你手上跑着 Go 1.24 以上的网络服务，得先确认内核版本和 MPTCP 的实际开启情况，再决定是升级内核还是关掉这个选项，别等公告出来才查。我觉得这条的价值在于它把 AI 找漏洞和默认配置的连带风险放在了一起，以后选 Go 版本时，默认行为的变化要当成变更项来看，不能只看语言特性。 [来源 · tonybai.com](https://tonybai.com/)

- **Go 1.25+ 的 synctest 用虚拟时间测并发，不用再靠 time.Sleep 猜**。文章讲的是 Go 1.25 起引入的 synctest 虚拟时间气泡，用来处理高并发场景里 goroutine 的时序测试问题，goroutine 初始只占 2KB 内存这个背景也提到了。你平时写并发代码如果靠 sleep 等状态，测试会又慢又不稳，这个机制能让时序在可控的虚拟时间里推进，值得在本地拿一个小例子跑一遍看效果。我觉得最实用的是它把「等多久才够」这种玄学问题变成了可复现的断言，不过要注意它只在 1.25+ 可用，老版本项目没法直接套。 [来源 · segmentfault.com](https://segmentfault.com/a/1190000048381152)
