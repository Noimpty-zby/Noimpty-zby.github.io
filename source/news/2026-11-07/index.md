## 工程实践与踩坑

- **WeKnora 源码拆解里提到 goroutine 泄漏的排查方法**。素材里说，WeKnora 是腾讯开源的 Go 高并发 RAG 与 Agent 项目；这篇从源码角度拆解的文章提到，goroutine 泄漏很隐蔽，表现为服务运行一段时间后内存持续升高，最后 OOM。排查方法是暴露 pprof 接口，观察 goroutine 数量是否只增不减。素材没有给出具体版本号，也没有给出复现步骤和代码位置。这对做 Go 后端和 AI Infra 的人有用，因为 RAG 服务里请求链路长、并发高，泄漏往往就藏在 channel 阻塞或 context 没有传递下去的地方；pprof 这条线索可以直接套用到自己的服务上。我觉得这条的价值在于它给了一个可操作的观察指标，而不是泛泛地谈并发好；不过文章没写复现步骤，真要照着排查，还得自己补上 pprof 的接入和 goroutine 快照对比。 [来源 · blog.csdn.net](https://blog.csdn.net/weixin_30984001/article/details/170072208)

- **Wails+Go+Vue 做批量 SSH 执行工具时用信号量控制并发度**。素材描述的是用 Go 的 goroutine 并发模型加 SSH 协议批量在多台主机上执行命令，并实时回传日志，通过信号量控制并发度来避免资源耗尽。具体的主机数量、Go 版本和实测数据，素材都没说。对做运维工具和后端的人来说，这个组合本身就有参考价值：goroutine 数量不受限制时，几百台机器同时建立 SSH 连接会耗尽文件描述符和内存，信号量是最省事的限制手段。我觉得这条可以当成一个最小骨架来看，它把「并发度」当成显式参数暴露出来，比那种一上来就 for 循环全量起 goroutine 的写法靠谱；但素材没给压测数字，并发度到底设多少，还是得按自己机器的 fd 上限来算。 [来源 · csdn.net](https://www.csdn.net/detail/webblog_79182479/66684)

## 能上手的小项目

- **一个能自动检查 AI 前端代码的 Skill 仓库**。这个仓库从 Anthropic 官方的 frontend-design Skill 出发，加了 24 个子命令，全挂在 /impeccable 下，还有 62 条确定性检测规则，由 CLI 和浏览器插件直接跑，不用 LLM 也不用 key。安装走 npx impeccable install，安装器会探测机器上装了哪些 Agent，可以加 --providers 和 --scope 指定工具和范围。作者自己跑了 39 个任务的基准，说代码量少 53%、token 省 45%、带测试的风险逻辑比例从 68% 提到 98%，这是自家口径，没法复核。对做 AI Infra 和后端的人来说，这东西能上手，范围也清楚：装一次，拿自己项目里的前端改动跑一遍规则，就能看到哪些是模型嘴上答应、规则不答应的地方。我觉得它真正的价值不在省 token，而在于把「AI 生成的代码要过确定性检查」这件事做成了可执行的一步，比只看 prompt 调优实在。 [来源 · cnblogs.com](https://www.cnblogs.com/jinjiangongzuoshi/p/23530628)
